# تحویل هستهٔ Studio — ۴ اکتبر ۲۰۲۶

این تغییر بر اساس `developer-card-roadmap-12w.md` فقط هستهٔ T0 تا T4 را اجرا می‌کند. فهرست ۴۵ گزینه، تعهد اجرای هم‌زمان همهٔ گزینه‌ها نیست؛ گالری، پرداخت، PWA، دامنهٔ اختصاصی، اتصال GitLab و گزینه‌های ردشده وارد این نسخه نشده‌اند.

## امکانات اضافه‌شده

| بسته | پیاده‌سازی |
|---|---|
| T0 | گردش‌کار GitHub Actions برای بک‌اند روی PostgreSQL، فرانت و Playwright؛ health endpoint و healthcheck کانتینر؛ تست‌های رگرسیون موجود |
| T1 | ویرایش مستقل فارسی/انگلیسی، عنوان و نقش و شعار و معرفی و متن تلگرام، بندهای معرفی و نقاط قوت و پیشنهادها و ویژگی‌ها؛ پنج لینک HTTPS؛ سه پروژهٔ عمومی با مسئله/راهکار/نتیجه در هر دو زبان؛ پیش‌نویس خصوصی؛ اعمال صریح روی کارت عمومی؛ تاریخچه و بازگردانی به نسخهٔ جدید |
| T2 | ثبت روزانهٔ اسنپ‌شات هنگام دریافت موفق گزارش، نمودار روند هر دوره، CSV خصوصی، نام پروژه برای هر جلسهٔ تایمر، یک هدف زمانی هفتگی، منابع عمومی معرفی |
| T3 | مدل کار پس‌زمینه و outbox در PostgreSQL، تحویل کار با Celery، ادغام درخواست‌های هم‌زمان، حفظ آخرین تحلیل موفق، حالت انتظار/اجرا/شکست و بازیابی کار قطع‌شده |
| T4 | پیش‌نمایش متن و تصویر انگلیسی، وضعیت ارسال، توقف ارسال دوباره هنگام UNKNOWN، دستور مدیریتی بررسی و ثبت نتیجه با سابقهٔ ممیزی |

متن دستی هیچ‌گاه داخل گزارش اصلی AI نوشته نمی‌شود. تغییر زبان AI جدید اجرا نمی‌کند. پاک‌کردن مقدار دستی، نمایش متن اصلی را برمی‌گرداند. بازگردانی فقط تنظیمات محتوای ویرایشگر را نسخه‌بندی می‌کند؛ تم و زبان همان تنظیمات مستقل موجود هستند.

ذخیرهٔ پیش‌نویس دکمهٔ صریح دارد؛ ذخیرهٔ خودکار یا ویرایشگر Markdown در این نسخه نیست. فیلدهای کیس‌استادی متن ساده‌اند. منبع هر پروژه یک لینک واقعی از مجموعهٔ پروژه‌های عمومی ذخیره‌شده است؛ این فهرست به معنی تأیید خودکار همهٔ ادعاهای متن AI نیست.

## قراردادها و حریم خصوصی

- `GET /api/health`: بررسی اتصال دیتابیس، بدون اطلاعات پیکربندی.
- `GET/POST /api/me/editor`: محتوای پیش‌نویس، متن اصلی، شمارهٔ نسخه و تاریخچه. عملیات `draft`، `apply` و `restore`؛ شمارهٔ نسخهٔ قدیمی پاسخ 409 می‌گیرد.
- `GET /api/me/snapshots` و `?format=csv`: حداکثر ۱۰۰ اسنپ‌شات اخیر، فقط مالک. در هر روز و هر جفت سال یک نقطه به‌روز می‌شود. CSV یک سطر برای هر اسنپ‌شات دارد؛ آمار هر سطر مجموع همان دوره است، نه تغییر نسبت به اسنپ‌شات قبلی.
- `GET/POST /api/me/goal`: یک هدف به دقیقه، از دوشنبه در منطقهٔ زمانی حساب. پیشرفت از تایمر محاسبه می‌شود.
- `POST /api/me/time/start`: فیلد اختیاری `project`، تا ۱۰۰ نویسه؛ محدودیت یک تایمر فعال حفظ شده است.
- `GET /api/me/jobs`: وضعیت ۲۰ کار اخیر خود کاربر؛ بدون تصویر، توکن یا متن خام خطا.
- `GET /api/me/telegram/preview`: متن کانال و دکمهٔ کارت، بدون ارسال و بدون فراخوانی AI.
- پاسخ عمومی کارت دارای `card_schema_version: 1` و فقط محتوای **اعمال‌شده** است؛ پیش‌نویس، تاریخچه، زمان، هدف، اسنپ‌شات و وضعیت کارها عمومی نمی‌شوند.

اعتبارسنجی هم هنگام نوشتن و هم هنگام ساخت پاسخ عمومی انجام می‌شود. مخزنی که دیگر در مجموعهٔ عمومی ذخیره‌شده نباشد از پروژه‌های نمایشی کنار گذاشته می‌شود. تازگی این مجموعه تابع مسیر فعلی تازه‌سازی GitHub است؛ بررسی لحظه‌ای خصوصی‌شدن مخزن در هر بازدید عمومی انجام نمی‌شود.

## اجرا و مهاجرت

پیش از استقرار از PostgreSQL نسخهٔ پشتیبان قابل‌بازیابی بگیرید. مهاجرت `0006` افزایشی است و محتوای AI یا جدول‌های قبلی را حذف نمی‌کند.

```sh
docker compose build backend frontend
docker compose run --rm backend python manage.py migrate --noinput
docker compose --profile jobs up -d
```

پس از اطمینان از سلامت backend، worker و beat، در محیط سرور قرار دهید:

```dotenv
STUDIO_ASYNC_JOBS=true
STUDIO_EDITOR=true
STUDIO_INSIGHTS=true
STUDIO_TELEGRAM_PREVIEW=true
```

سپس backend، celery و celery-beat را با همان محیط بازسازی/راه‌اندازی کنید:

```sh
docker compose --profile jobs up -d --force-recreate backend celery celery-beat
docker compose logs --tail=100 backend celery celery-beat
```

`STUDIO_ASYNC_JOBS` به‌صورت پیش‌فرض خاموش است تا نصب بدون worker کارهای معلق تولید نکند. در حالت خاموش، تحلیل با مسیر همگام موجود کار می‌کند و ارسال تلگرام همچنان تلاش پایدار ثبت می‌کند ولی همان درخواست آن را اجرا می‌کند. با روشن‌شدن پرچم، outbox هر ۱۰ ثانیه کارهای در صف را تحویل worker می‌دهد. فقط یک beat اجرا شود. سرویس `telegram-maintenance` همچنان مسئول سیاست عضویت است؛ این کار دوباره به beat اضافه نشده است.

تصویر انگلیسی تلگرام پیش از صف‌شدن توسط مرورگر ساخته و روی کار ذخیره می‌شود. پس از ثبت موفق درخواست، بازبودن مرورگر لازم نیست. اگر مرورگر پیش از آپلود تصویر بسته شود، ارسال اولیه هنوز ثبت نشده و در ورود بعدی دوباره بررسی می‌شود. رندر تصویر روی سرور جزو این نسخه نیست.

فراخوانی AI همچنان تمام خروجی دوزبانه را با همان قرارداد یک پرامپت تهیه می‌کند. زمان انقضای محتوای موفق ۲۴ ساعت است و تغییر fingerprint مهم نیز آن را نامعتبر می‌کند. این بررسی هنگام استفاده انجام می‌شود؛ تولید روزانه برای حساب‌های غیرفعال اضافه نشده است.

## تلگرام و وضعیت نامشخص

چرخهٔ کار `pending → running → succeeded/failed/unknown` است. انتشار اولیه خودکار و انتشار بعدی دستی با همان شرط هفت روز و نبود پست قبلی باقی می‌ماند. مهلت عضویت دو ساعت حفظ می‌شود؛ اختلال در بررسی عضویت به معنی عدم عضویت نیست.

قطع ارتباط هنگام ارسال ممکن است بعد از پذیرش پیام توسط تلگرام اتفاق افتاده باشد. بنابراین UNKNOWN خودکار تکرار نمی‌شود. این راهکار ادعای exactly-once ندارد. کار تلگرام که بیش از ۳۰ دقیقه در حالت running بماند نیز UNKNOWN می‌شود؛ کار AI قطع‌شده failed می‌شود و آخرین خروجی موفق باقی می‌ماند.

ادمین پس از بررسی واقعی کانال، یکی از این دو دستور را اجرا می‌کند؛ مقدارهای مثال باید با واقعیت جایگزین شوند:

```sh
# فقط وقتی نبود پیام بررسی و تأیید شده است:
docker compose exec backend python manage.py reconcile_telegram JOB_ID \
  --actor ADMIN_NAME --note 'شرح بررسی کانال' --confirmed-absent

# وقتی پیام موجود پیدا شده است؛ زمان واقعی انتشار به میلی‌ثانیهٔ Unix:
docker compose exec backend python manage.py reconcile_telegram JOB_ID \
  --actor ADMIN_NAME --note 'شرح شناسایی پیام' \
  --message-id MESSAGE_ID --published-at UNIX_MILLISECONDS
```

دستور دوم زمان واقعی را برای محاسبهٔ هفت روز و دو ساعت ثبت می‌کند. هر تصمیم در `JobAudit` می‌ماند. این دستور هیچ پیامی ارسال نمی‌کند. تأیید نبود پیام فقط محدودیت UNKNOWN را رفع می‌کند؛ شرایط انتشار قبلی همچنان هنگام تلاش بعدی بررسی می‌شوند.

## بازگشت و بهره‌برداری

- برای توقف رابط ویرایش یا بینش از پرچم‌های مربوط استفاده کنید؛ داده پاک نمی‌شود.
- برای متوقف‌کردن تولید کار جدید، `STUDIO_ASYNC_JOBS=false` کنید. پیش از خاموش‌کردن worker، کارهای pending/running را بررسی و تخلیه کنید. بازگشت به کد قدیمی در حالی که ارسال نامشخص یا در حال اجرا وجود دارد می‌تواند محافظت در برابر تکرار را دور بزند؛ ابتدا آن‌ها را تعیین تکلیف کنید.
- مهاجرت را برای rollback معکوس نکنید؛ جدول‌های افزوده و سابقه‌ها را حفظ کنید.
- لاگ `studio_job` شامل شناسه، نوع، وضعیت و مدت است؛ شامل توکن یا محتوای خصوصی نیست. وضعیت دیتابیس در `/api/health` و سلامت worker در لاگ و صف مشاهده می‌شود؛ health endpoint سلامت سرویس AI/Telegram را تضمین نمی‌کند.
- تصویر کار بعد از اتمام یا UNKNOWN پاک می‌شود. سیاست پاک‌سازی بلندمدت revision/snapshot/audit باید با سیاست محصول تعیین شود؛ پاک‌سازی خودکار تاریخچه در این نسخه انجام نشده است.

## اعتبارسنجی و حدود تحویل

تست‌ها شامل رگرسیون API عمومی، ترجیحات دوزبانه، قرارداد AI، چرخهٔ تلگرام، نسخهٔ متعارض ویرایشگر، جداسازی پیش‌نویس، نگهداری متن اصلی، جلوگیری از ارسال مجدد UNKNOWN، outbox، قطع worker، هدف هفتگی و تایمر پروژه‌دار هستند. آزمون PostgreSQL هم‌زمانی ایجاد کار را نیز بررسی می‌کند. تست مرورگر مسیر ویرایش و بازدید عمومی را در موبایل و دسکتاپ پوشش می‌دهد.

نتیجهٔ بررسی محلی این تحویل: ۴۸ تست بک‌اند روی PostgreSQL موقت و ۲۶ تست Playwright پاس شدند؛ build فرانت، بررسی Compose و سازگاری migration نیز موفق بودند. مسیر ویرایشگر در اسکرین‌شات موبایل و دسکتاپ بررسی شد.

ساخت فایل CI به معنی اجرای موفق آن روی GitHub نیست؛ نتیجهٔ CI پس از push در Actions مشخص می‌شود. آزمون‌های provider با mock انجام می‌شوند و این تغییر در این مرحله به سرور زنده مستقر نشده است. پیش از فعال‌سازی واقعی، smoke test محیط staging با حساب و کانال آزمایشی لازم است.

KPIهای activation، زمان رسیدن به اولین ارزش، بازگشت هفتهٔ چهارم، اشتراک و هزینهٔ هر کاربر فعال هنوز baseline واقعی ندارند. از تعداد تست موفق نمی‌توان نتیجهٔ رشد محصول گرفت. هزینه باید هزینهٔ همهٔ تلاش‌ها، از جمله درخواست‌های ناموفق و retry، تصویر، زیرساخت و ذخیره‌سازی را شامل شود؛ قیمت فروش یا آمار ساختگی تعیین نشده است.
